## Tech Stack

| Layer | Technology | Why I Chose It |
|-------|-----------|----------------|
| **Framework** | FastAPI (Python) | Async-ready, auto-generates OpenAPI spec, built-in request validation via Pydantic, minimal boilerplate |
| **Database** | SQLite + SQLAlchemy ORM | Zero-config, file-based DB perfect for a lightweight deploy. SQLAlchemy makes it trivially swappable to PostgreSQL |
| **Authentication** | JWT (python-jose) | Stateless auth — no server-side sessions to manage. Tokens expire in 24h |
| **Password Hashing** | bcrypt (via passlib) | Industry-standard adaptive hashing — resistant to brute-force and rainbow table attacks |
| **Deployment** | Render.com (Free Tier) | Git-based auto-deploy, zero DevOps overhead, HTTPS out of the box |
| **Python Version** | 3.11.9 | Stable, fast, full wheel support for all dependencies |

## Architecture

```
Client (HTTP)
    │
    ▼
┌──────────────────────────┐
│  FastAPI Application     │
│  ├── Auth Middleware      │  ← JWT Bearer token validation
│  ├── Route Handlers       │  ← Business logic
│  └── SQLAlchemy ORM       │  ← Data access layer
│         │                 │
│         ▼                 │
│  ┌──────────────┐        │
│  │   SQLite DB   │        │
│  │  ┌─────────┐ │        │
│  │  │ users    │ │        │
│  │  │ notes    │ │        │
│  │  │ shares   │ │        │
│  │  │ versions │ │        │
│  │  └─────────┘ │        │
│  └──────────────┘        │
└──────────────────────────┘
```

### Database Schema

- **users** — id (UUID), email (unique), password_hash, created_at
- **notes** — id (UUID), title, content, owner_id (FK→users), created_at, updated_at
- **note_shares** — note_id (FK→notes), user_id (FK→users) — composite PK, many-to-many
- **note_versions** — id (UUID), note_id (FK→notes), title, content, version_number, saved_at

All foreign keys use `ON DELETE CASCADE` so deleting a user or note cleans up related records automatically.

## Custom Feature: Note Version History

### What it does

Every time a note is updated via `PUT /notes/{id}`, the system **automatically snapshots the previous content** into a `note_versions` table before overwriting it. This creates a complete, tamper-proof edit trail.

Users can:
1. **View history** — `GET /notes/{id}/history` returns every past version with timestamps
2. **Revert** — `POST /notes/{id}/revert/{version_number}` restores any past version
3. **Undo a revert** — The current state is snapshotted before reverting too, so every action is undoable

### Why this feature matters

| Problem | How Version History Solves It |
|---------|-------------------------------|
| Accidental overwrites | One API call to restore any past version |
| "What did this note say yesterday?" | Full audit trail with timestamps |
| Fear of editing | Users edit freely knowing nothing is lost |
| Collaborative confusion (shared notes) | Track how content evolved after sharing |
| Accidental revert | Even reverts are reversible — the current state is saved before restoring |

### Why I chose this over other features

- **Tags/Labels** — organizational, but doesn't protect user data
- **Note pinning** — cosmetic, doesn't add real value
- **Markdown rendering** — frontend concern, not backend
- **Note versioning** — directly prevents data loss, which is the #1 user complaint in notes apps. Google Docs, Notion, and Apple Notes all have version history. It signals product maturity.

### Example flow

```
1. Create note         → "Draft ideas" / "First draft content"
2. Update note         → "Draft ideas" / "Revised content"
   └── Version 1 saved: "First draft content"
3. Update note again   → "Draft ideas" / "Final content"
   └── Version 2 saved: "Revised content"
4. GET /history        → [v1: "First draft", v2: "Revised content"]
5. Revert to v1        → Note restored to "First draft content"
   └── Version 3 saved: "Final content" (so you can undo the revert)
```

## Edge Cases & Validations

| Scenario | Behavior |
|----------|----------|
| Register with duplicate email | 409 Conflict |
| Register with invalid email (no @) | 400 Bad Request |
| Register with short password (<8 chars) | 400 Bad Request |
| Login with wrong credentials | 401 "Invalid email or password" |
| Access note you don't own/isn't shared | 403 Access Denied |
| Access non-existent note | 404 Not Found |
| Update/delete note you don't own | 404 (doesn't leak existence) |
| Share with non-existent user | 404 User not found |
| Share note with yourself | 400 Bad Request |
| Share same note twice with same user | Idempotent (no duplicate, returns 200) |
| Create note with empty title | 400 Bad Request |
| Update note with empty title | 400 Bad Request |
| Expired JWT token | 401 Invalid or expired token |
| Missing Authorization header | 403 Not authenticated |
| Revert to non-existent version | 404 Version not found |
| Email casing (Test@Email.COM) | Normalized to lowercase, treated as same user |

## Security Decisions

| Decision | Rationale |
|----------|-----------|
| bcrypt for passwords | Adaptive cost factor, 60+ years of cryptanalysis, resistant to GPU attacks |
| JWT with expiration (24h) | Stateless, no session store needed; tokens expire to limit damage from theft |
| Email normalization (lowercase + trim) | Prevents duplicate accounts via casing tricks |
| Owner-only mutations | Only the note owner can update, delete, or share — shared users get read access |
| 404 for unauthorized mutations | Returns "not found" instead of "forbidden" to avoid leaking note existence to non-owners |
| CASCADE deletes | Deleting a user removes all their notes, shares, and versions — no orphaned data |
| SECRET_KEY via env var | Not hardcoded in source; set in Render dashboard |

## How to Run Locally

```bash
# Clone
git clone https://github.com/Sampada-23-00/notes-app.git
cd notes-app

# Install dependencies
pip install -r requirements.txt

# Run
uvicorn main:app --reload --port 8000

# Open in browser
# http://localhost:8000/docs (Swagger UI)
# http://localhost:8000/openapi.json (OpenAPI spec)
```

